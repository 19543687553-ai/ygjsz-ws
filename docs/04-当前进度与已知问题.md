## 2. 已知问题（按用户反馈排序）

### P0-1 战场内不刷怪物

**用户原话**：「游戏对局内不刷怪物」。

**已抓到的证据**（线上日志 2026-10-24）：

```
[TDServer] 阵营1,第0帧,执行客户端操作类型 出怪,参数{"frame":0}
[TDServer] delegate操作:阵营:1：第0帧,实际效果:出怪时机
```
→ 说明**波次表加载成功、出怪流程已启动**（不是「配置找不到」）。

同时：
```
[TDServer] 上阵英雄失败，此英雄已在阵上，heroCode = 50000001     × N
[TDServer] 英雄终极建造失败，找不到 ... 的武将建筑的entityId
阵营1 资源 370025          ← 玩家
阵营11 资源 6 / 阵营10 15 / 阵营9 11 / 阵营8 10 / 阵营7 10   ← 机器人
```

**波次来源（重要）**：
```js
// index.b7927.js 本地战场 onLogicTick(tick=0)
var r = this._room.getTemplateInfoCfg();            // ← 来自客户端配置，不是服务器
this._delegateServer.onCreepInfoPPush(r.waveSchedules, r.templateInfos);
this._createCoreField();
// tick=2: this._createCoreBuilding(); this._room.setStartCreep();
```
→ 所以**怪物不由服务器发包控制**，问题在客户端战场逻辑（阵营/房间/资源数据异常导致早退或目标为空）。

**下一步（必须做）**：
1. 起 Playwright，进一局战场，每 500ms 采样：
   - `cc.director.getScene()` 里敌人节点数量
   - `BattleModule.Ins._battleList[0]` 的 `_room` / 各 camp 的 `resources` / `targetRoomId`
   - `window.__battle` 里 `creepList.length`
2. 若敌人数一直是 0，去 `setStartCreep()` 下断点（注入 `console.log`），看 `nextCreepFrame` 是否被设成 `Infinity` / `-1`。
3. 检查 `BattleGroundLO.get(code)` 的 `houseNum`：6 个玩家需要 ≥ 6 个房间，否则目标房间越界。

### P0-2 队友不升级房门/床、不出战英雄

**根因（高置信）**：`battleStartGameP()` 里 5 个机器人**共用玩家同一份 heroList**：
```js
const mine = heroListOf(p);
players = [battlePlayerInfo(p, p.playerId, mine, 6, true)];
for (const id of ROBOT_IDS) players.push(battlePlayerInfo(p, id, mine, 0, false));  // ← 全用 mine
```
客户端 `TDServer` 上阵时按 `heroCode` 去重 → 机器人拿到的英雄「已在阵上」→ 直接失败：
```
[TDServer] 上阵英雄失败，此英雄已在阵上，heroCode = 50000001
```

**官方真实数据**（抓包 `StartGameP.playerInfos`，5 个机器人各不相同）：

| playerId | 英雄 code | uuid | attr | fightCap |
|---|---|---|---|---|
| 11041 | 50000033 | `"50000033"` | `{1:7}` | ~135-140 |
| 11012 | 50000018 | `"50000018"` | `{1:7}` | ~ |
| 11014 | 50000035 | `"50000035"` | `{1:7}` | ~ |
| 11006 | 50000036 | `"50000036"` | `{1:7}` | ~ |
| 11009 | 50000020 | `"50000020"` | `{1:7}` | ~ |

> 机器人 `uuid` **就是 code 字符串**，`skills` 可以留空，`level:1, section:0`。

**修法**：
1. 在 `server.mjs` 加 `ROBOT_HEROES = { 11041:[...], ... }`，`battlePlayerInfo` 按 id 取对应英雄，不要复用 `mine`。
2. 机器人 `attr` 用 `{1: 7}`（不是 100），`fightCap` 135~140。
3. 机器人资源低是因为客户端按「床等级 + 时间」产出，正常；但如果 P0-1 修好了（有怪可打、有击杀奖励），机器人会自然升级。

### P1-1 队友和玩家 / 队友之间可能在同一房间

**客户端逻辑**（`AdvBattleRoom.initPlayerEnties`）：
```js
t.sort((a,b)=>a.playerId-b.playerId);   // 11006,11009,11012,11014,11041,67820771
isRobot ? setCampId(r++) : setCampId(n++);
// level>1：e.setTargetRoomId(c++)  → 机器人 1,2,3,4,5；真人 6
```
**线上日志实测**：
```
阵营1 选择房间 {"roomId":2}     ← 真人（玩家手动点到房间 2）
阵营8 选择房间 {"roomId":2}     ← 机器人 11009（targetRoomId=2）
阵营9 3 / 阵营10 4 / 阵营11 5
```
→ **撞房 = 玩家手动选房覆盖了自己的 targetRoomId(6)**。机器人的目标房间是对的。

**修法（二选一）**：
- **A（推荐）**：给真人 `roomCode=6`（已经是），并在客户端 hook `SelectRoom` 操作：当 `campId==1 && frame<30` 时强制 `roomId=6`；或者干脆把「点房间底座」的点击在开局阶段屏蔽（`屏蔽点击` 提示已有）。
- **B**：不拦截，改成 UI 引导——在玩家房间底座上显示「你的房间：6」，点别的房间弹提示。

### P1-2 GM 物品 ID 未知 / 反应延迟 / 没有存档

- **物品 ID**：`sy_api/data/items.json` 有 1732 条，字段含 `code/name/quality/icon/...`。
  → 做一个 `sy_api/gm.php`：名字搜索 → 出 code → 一键发（见 `00` 第 4 步）。
- **延迟**：`5/174` 回包后要等客户端处理推送。现在服务端已经立刻推 `13/5`/`23/9`/`11/12`，但如果界面带飞卡动画（`clientReward`），会被动画挡 1~2 秒。可以给 GM 回包**不带** `clientReward`（只推最新数值），界面就会瞬间刷新。
- **存档**：机制见 `docs/02` G1。用户感知「没有存档」通常是：
  ① 关掉页面后重进，`state/player.php` 没写成功（检查 `internal.php` 返回）；
  ② 多端同时玩覆盖；
  ③ 客户端本地缓存（`localStorage`）覆盖了服务端数据。
